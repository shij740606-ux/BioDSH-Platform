# BioDSH 产品化工程规范

## 适用范围

本规范适用于平台后端、桌面端、Worker、生信工作流、部署脚本和数据迁移。所有功能都按最终提供给真实用户使用设计。原型阶段可以缩小功能范围，但不能绕过配置、安全、升级和运维边界。

## 配置与环境

- 环境分为 `development`、`test`、`staging` 和 `production`，使用同一份代码构建产物。
- 域名、端口、目录、数据库、资源额度、镜像、日志级别和功能开关全部从配置读取。
- 源码只保存安全的开发示例；生产密钥、密码和令牌必须由部署环境注入。
- 生产配置缺失或不安全时必须启动失败，不能静默回退到开发默认值。
- 配置项必须有类型、范围、说明、默认策略和升级兼容策略。

## API 与兼容

- 对外 API 使用版本前缀，例如 `/api/v1`。
- 客户端通过 `/.well-known/biodsh-platform` 发现服务能力和当前 API 路径，避免部署配置与客户端重复写死。
- 已发布字段不随意改名或改变含义；删除接口必须经历弃用期。
- 请求必须校验，错误使用稳定的机器可读错误码和可追踪请求 ID。
- 创建、提交、重试等接口设计幂等键，避免网络重试产生重复任务。
- 桌面端和 Worker 在连接时交换协议版本和能力清单，拒绝不兼容组合。

## 数据与迁移

- 数据库结构只能通过 Alembic 迁移改变，禁止生产环境自动建表。
- 每次迁移说明升级、回滚、锁表风险和数据转换成本。
- 文件和任务保存内容指纹、执行版本、创建者、时间和来源。
- 数据删除采用明确的生命周期策略，并记录审计事件。
- 发布前验证备份与恢复；恢复测试通过才算备份有效。

## 安全

- 用户密码采用 Argon2id；访问令牌短期有效，刷新令牌可撤销并轮换。
- 桌面端敏感凭据进入操作系统安全存储，不写入普通 JSON 配置。
- 项目数据、任务和结果全部执行服务端权限检查，不能只依赖界面隐藏。
- Worker 使用独立节点身份、最小权限和可撤销凭据。
- 日志不得输出密码、令牌、原始敏感数据或完整认证头。
- 对外服务使用 HTTPS；内部数据库不暴露公共端口。

## 可观测性与运维

- 服务提供存活和就绪探针，并输出结构化日志。
- 每个请求、任务和 Worker 执行都有关联 ID，可从用户操作追踪到服务器日志。
- 记录请求延迟、错误率、队列长度、任务耗时、失败原因、节点资源和磁盘容量。
- 告警包含影响范围、发生时间、相关版本和建议操作。
- 发布使用版本目录或不可变镜像，支持健康检查失败时自动回退。

## 测试与发布门禁

每项功能至少满足以下条件才能进入主分支：

1. 单元测试覆盖业务规则，集成测试覆盖数据库和外部边界。
2. 权限功能包含允许、拒绝和跨项目越权测试。
3. 数据库迁移完成升级与回滚验证。
4. 桌面端、平台和 Worker 的协议兼容测试通过。
5. 格式检查、静态检查、依赖锁定和构建在 CI 中通过。
6. 配置示例、运维说明、失败处理和用户可见行为同步更新。
7. staging 完成小数据端到端验证后才允许发布 production。

## 架构约束

- 当前使用 FastAPI 单体平台和 PostgreSQL，按模块划分边界，不提前拆微服务。
- 任务队列先使用 PostgreSQL 的事务锁实现；达到经过测量的瓶颈后再引入专用消息系统。
- 单服务器文件使用受控本地目录；确有多机共享需求后启用 NFS 或对象存储适配器。
- 执行器通过统一接口支持本机进程、容器和 Slurm，业务层不拼接远程命令。
- 生信流程必须有版本、输入输出 Schema、资源声明、参考数据版本和可复现运行记录。

## 阶段完成定义

“接口已经能调用”只表示开发中。一个阶段只有同时具备代码、迁移、配置、安全、测试、监控、部署、回滚和文档，且在 staging 验证完成，才可以标记为可发布。任何临时桥接机制都必须标注替换阶段，并在用户发布门禁前移除。
